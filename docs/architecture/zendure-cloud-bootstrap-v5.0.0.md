# V5.0.0: Zendure Cloud account bootstrap

Status: implementation boundary for issue #322

## Purpose

The first native Zendure connection is a read-only account bootstrap. A user
provides the App/Home Assistant token generated by Zendure. BSFAI decodes the
regional HTTPS endpoint and App key, signs one `POST /api/ha/deviceList`
request, and parses every returned main device. There is no device write,
MQTT connection, entity creation, backend switch, or control activation in
this step.

The actual Home Assistant form and its password-style token selector are wired
when native onboarding is introduced. The parser and live validation client in
this issue are the single validation path that form must call; the token must
never be copied into a normal text field, error description, log, or
diagnostic export.

## Security boundary

`ZendureAppToken` and `CloudMqttCredentials` belong exclusively to the Cloud
transport adapter. Their fields are excluded from representations. Exceptions
crossing the adapter expose only a fixed reason such as `invalid_token`,
`timeout`, or `cannot_connect`; neither response bodies nor nested exception
messages are surfaced.

The Core receives only `DiscoveryCandidate` values. Device keys, serials and
product identifiers remain internal identity data and must pass through the
central Zendure diagnostic sanitizer before any export. Unknown response
fields are recorded only by field name for capture planning; their values are
not retained by the bootstrap model.

## Existing-installation safety

All account devices are unbounded and retained as passive candidates. Calling
`register_candidates()` does not create a logical system, HA device or entity,
does not alter the selected transport, and cannot activate control. An
existing V4 ConfigEntry therefore remains the sole active logical system until
the later migration flow presents candidates and the user explicitly confirms
the physical association.

Duplicate display names are valid. Duplicate stable identities fail the whole
bootstrap because silently collapsing them could bind the wrong hardware.
Unknown product models remain visible but unsupported and observation-only.

## Failure handling

- malformed token or unsafe/non-HTTPS endpoint: `invalid_token`;
- rejected account request: `invalid_or_expired_token`;
- bounded network or JSON failure: `timeout` or `cannot_connect`;
- changed/incomplete response: `invalid_response` or `incomplete_device`;
- empty account: `no_devices`;
- missing MQTT bootstrap block: `no_mqtt_credentials`;
- repeated native identity: `duplicate_device_id`.

The request is deliberately not retried here. Onboarding may invite an explicit
retry, while runtime refresh policy belongs to the later Cloud transport.
